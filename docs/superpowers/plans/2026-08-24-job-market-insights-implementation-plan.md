# План реализации сервиса поиска и анализа вакансий

Дата: 24 августа 2026 года  
Основание: `docs/superpowers/specs/2026-08-24-job-market-insights-design.md`  
Статус: готов к выполнению после подтверждения пользователя

## Результат

Превратить существующий демонстрационный Next.js-интерфейс в работающий сервис:

`форма → Turnstile → Apify → вакансии → OpenRouter → отчёт → Vercel`.

План не предусматривает Redis, регистрацию, загрузку резюме или автоматический перевод профессий. Лимит и кэш остаются браузерными, как согласовано.

## Этап 0. Подготовить рабочую копию

### Действия

1. Проверить контрольную сумму и сохранить исходный `job-market-insights.zip` без изменений.
2. Убедиться, что в рабочей папке нет файлов с такими же именами, как внутри архива.
3. Распаковать содержимое архива в корень проекта, сохранив существующую папку `docs/`.
4. Проверить наличие `package.json`, `pnpm-lock.yaml`, `app/`, `components/`, `lib/` и `public/`.
5. Проверить, не появились ли в распакованных файлах секреты или `.env` со значениями.
6. Загрузить доступные в рабочей среде Node.js и pnpm и установить зависимости строго по существующему lock-файлу.
7. Запустить исходную production-сборку и отдельно `tsc --noEmit`, зафиксировав все исходные ошибки до изменения кода.

### Файлы

- `package.json`;
- `pnpm-lock.yaml`;
- `next.config.mjs`;
- `tsconfig.json`.

### Критерий готовности

Проект распакован, зависимости установлены, исходное состояние воспроизводится, архив сохранён.

## Этап 2. Реализовать адаптер Apify

### Действия

1. Перед кодированием сверить актуальную Input Schema Actor `s3dtSTZSZWFtAVLn5`, не угадывая названия фильтров страны, города и уровня.
2. Сформировать Actor input из формы:
   - `timeRange: "7d"`;
   - `limit: 20`;
   - текстовое описание;
   - основное и дополнительное названия как точные поисковые варианты;
   - поддерживаемые фильтры страны, города, формата и уровня;
   - AI-поля источника только там, где они нужны для нормализации.
3. Вызывать Actor только на сервере через официальный `apify-client` либо официальный REST API с Bearer-заголовком. Токен нельзя передавать в URL.
4. Ограничить ожидание Actor и корректно различать timeout, ошибку авторизации, исчерпанный лимит и пустую выдачу.
5. Преобразовать сырой ответ в внутренний тип `NormalizedJob`.
6. Не передавать клиенту сырой HTML описания. Использовать очищенный текст и ограничивать его размер перед LLM.
7. Отбрасывать записи без валидного идентификатора, названия или исходной ссылки.
8. Сохранить обезличенные тестовые фикстуры сырого ответа без токенов и персональных данных.

### Новые файлы

- `lib/apify/client.ts`;
- `lib/apify/build-input.ts`;
- `lib/apify/normalize-job.ts`;
- `lib/apify/errors.ts`;
- `lib/apify/__fixtures__/jobs.json`;
- `lib/apify/build-input.test.ts`;
- `lib/apify/normalize-job.test.ts`.

### Критерий готовности

На фикстурах формируется корректный Actor input, а разнообразные ответы Apify превращаются в устойчивый массив из не более чем 20 нормализованных вакансий.

## Этап 3. Реализовать зарплатную классификацию и проверяемые факты

### Действия

1. Нормализовать известные minimum/maximum, валюту и период оплаты, не разбирая неоднозначный текст догадками.
2. Разделять вакансии на:
   - проходят минимальную зарплату;
   - зарплата не указана;
   - валюта или период несопоставимы;
   - достоверно ниже минимума.
3. Не конвертировать валюты.
4. Детерминированно вычислять частотность навыков, количество вакансий с зарплатой и сопоставимые диапазоны.
5. Подготовить фактическую сводку, которая будет передана LLM как единственный источник числовых утверждений.

### Новые файлы

- `lib/analysis/classify-salary.ts`;
- `lib/analysis/build-facts.ts`;
- `lib/analysis/classify-salary.test.ts`;
- `lib/analysis/build-facts.test.ts`.

### Критерий готовности

Пограничные случаи зарплат покрыты тестами; все числа отчёта можно воспроизвести без LLM.

## Этап 4. Подключить Cloudflare Turnstile

### Действия

1. Добавить клиентский компонент Turnstile с управляемыми состояниями: готов, проверен, истёк, ошибка.
2. Для локальных автоматических тестов использовать официальные тестовые site key и secret key Cloudflare.
3. На сервере вызывать `POST https://challenges.cloudflare.com/turnstile/v0/siteverify`.
4. Передавать secret, клиентский response token и, при наличии, адрес запроса.
5. Отклонять пустой, истёкший, повторно использованный или неподтверждённый токен до запуска Apify.
6. После завершения или ошибки сбрасывать виджет, поскольку Turnstile-токен одноразовый.

### Новые файлы

- `components/turnstile-widget.tsx`;
- `lib/turnstile/verify.ts`;
- `lib/turnstile/verify.test.ts`.

### Критерий готовности

Положительный тестовый токен пропускает запрос; отрицательный, повторный и истёкший токены блокируют его до внешних платных вызовов.

## Этап 5. Реализовать OpenRouter-анализ

### Действия

1. Описать строгую JSON Schema отчёта с `additionalProperties: false`.
2. Сформировать системную инструкцию на русском языке:
   - использовать только переданные вакансии и фактическую сводку;
   - не объявлять вывод анализом всего рынка;
   - не придумывать зарплаты, требования или временные тренды;
   - использовать только известные идентификаторы вакансий;
   - вернуть 3–5 реалистичных шагов обучения.
3. Вызвать `POST https://openrouter.ai/api/v1/chat/completions` с моделью `openrouter/free`.
4. Запросить `response_format.type = "json_schema"`, strict schema и routing с `require_parameters: true`.
5. Выполнять LLM-запрос без внутреннего стриминга: внешний API-маршрут передаст клиенту готовое событие `analysis`.
6. Валидировать JSON повторно через Zod.
7. Отбрасывать неизвестные job ID и ограничивать match диапазоном 0–100.
8. При структурной ошибке сделать одну повторную попытку с теми же фактами и более короткой инструкцией исправления.
9. Если обе попытки неуспешны, вернуть частичный успех: вакансии есть, анализа нет.

### Новые файлы

- `lib/openrouter/report-schema.ts`;
- `lib/openrouter/prompt.ts`;
- `lib/openrouter/client.ts`;
- `lib/openrouter/errors.ts`;
- `lib/openrouter/prompt.test.ts`;
- `lib/openrouter/report-schema.test.ts`.

### Критерий готовности

Мок-тесты подтверждают валидный отчёт, отклонение неизвестных вакансий, одну повторную попытку и корректный частичный результат при полном отказе LLM.

## Этап 6. Создать единый потоковый API-маршрут

### Действия

1. Создать `POST /api/analyze` как Next.js Route Handler.
2. Проверить Content-Type, размер тела и входную Zod-схему.
3. Проверить наличие обязательных серверных переменных окружения без вывода их значений.
4. Проверить Turnstile.
5. Запустить Apify, нормализовать вакансии и сформировать фактическую сводку.
6. Вернуть поток `application/x-ndjson; charset=utf-8`.
7. Отправлять события в порядке:
   - `status: searching`;
   - `jobs`;
   - `status: analyzing`;
   - `analysis` либо `warning`;
   - `complete`.
8. На ошибке до получения вакансий отправлять терминальное `error`.
9. Не включать в ответы сырые upstream-ошибки, заголовки авторизации, prompt или секреты.
10. Добавить тайм-ауты и отмену downstream-запросов при закрытии клиентского соединения.
11. Перед развёртыванием проверить фактический лимит длительности Vercel Function выбранного тарифа и установить допустимый `maxDuration` без превышения тарифа.

### Новые файлы

- `app/api/analyze/route.ts`;
- `lib/stream/ndjson.ts`;
- `app/api/analyze/route.test.ts`.

### Критерий готовности

Интеграционный мок-тест получает вакансии раньше анализа, сохраняет вакансии при сбое OpenRouter и не вызывает Apify при ошибке Turnstile.

## Этап 10. Проверить проект локально

### Автоматические проверки

Выполнить последовательно:

```text
pnpm run typecheck
pnpm test
pnpm run build
```

Если сборка не включает lint, запустить существующий lint-скрипт; не добавлять линтер только ради формального шага.

### Контролируемая проверка с реальными сервисами

1. Пользователь вводит реальные секреты только в `.env.local` или через защищённый интерфейс окружения.
2. Выполняется один запрос с лимитом 20 вакансий и `timeRange: 7d`.
3. Проверяется, что вакансии реальные и каждая ссылка ведёт к исходному объявлению.
4. Проверяется, что ответ OpenRouter использует только job ID из выдачи.
5. Проверяется частичный результат искусственным отключением OpenRouter после получения вакансий.
6. Выполняется secret scan исходников, собранного клиентского JavaScript и сетевых ответов.

### Визуальная проверка

После успешной сборки проверить в браузере:

- desktop и mobile;
- пустую форму;
- поиск;
- появление вакансий до анализа;
- отчёт;
- пустую выдачу;
- ошибку Turnstile;
- недоступный OpenRouter;
- повтор из кэша;
- достижение лимита.

### Критерий готовности

Все автоматические проверки проходят, один реальный запрос подтверждён, секреты не видны клиенту.

## Этап 11. Подготовить Git и Vercel

### Git

Рабочая папка сейчас не является Git-репозиторием. Перед публикацией отдельно согласовать с пользователем один способ:

- создать новый локальный репозиторий и подключить новый GitHub-репозиторий;
- либо публиковать напрямую через Vercel CLI без GitHub.

Нельзя инициализировать репозиторий, создавать внешний репозиторий или отправлять код без отдельного подтверждения.

### Vercel Preview

1. Создать или подключить проект Vercel.
2. Добавить четыре переменные окружения для Preview.
3. Создать Turnstile widget для preview hostname либо временно использовать официальный тестовый ключ только в непубличной проверке.
4. Развернуть Preview.
5. Проверить публичный Preview URL как обычный посетитель.
6. Убедиться, что Vercel Function успевает завершить Apify и OpenRouter в пределах тарифа.

### Vercel Production

1. Добавить Production hostname в разрешённые Turnstile hostnames.
2. Добавить Production secrets.
3. Выполнить новое production-развёртывание после добавления переменных.
4. Повторить один полный пользовательский сценарий.
5. Проверить кэш, исходные ссылки, мобильную версию и отсутствие секретов.

### Критерий готовности

Публичный Vercel URL проходит полный сценарий как обычный посетитель; Preview и Production используют собственные корректные переменные окружения.

## Контрольные точки выполнения

1. **База воспроизводится:** распакованный исходный интерфейс собирается.
2. **Данные устойчивы:** схемы, Apify-нормализация и зарплаты покрыты тестами.
3. **Безопасный вход:** Turnstile проверяется сервером до Apify.
4. **Частичный результат:** вакансии приходят раньше аналитики.
5. **LLM ограничена фактами:** отчёт проходит строгую схему и серверную проверку.
6. **Демо удалено:** интерфейс не использует `lib/data.ts` и таймеры.
7. **Локальная готовность:** typecheck, тесты, build и один реальный вызов успешны.
8. **Публичная готовность:** полный сценарий подтверждён на Vercel URL.

## Риски, которые проверяются в первую очередь

- Actor может выполняться дольше лимита Vercel Function выбранного тарифа.
- Названия реальных полей Actor input могут отличаться от примеров; использовать только актуальную Input Schema.
- Бесплатная модель может быть временно недоступна или не найти провайдера со strict JSON Schema.
- Двадцать полных описаний могут быть слишком объёмными; перед LLM передавать ограниченный текст и детерминированную сводку.
- Зарплаты в источниках имеют разные валюты и периоды; неоднозначные значения не сравнивать.
- Браузерный лимит обходится и не защищает от целевой атаки; это принято только для учебной версии.
- Turnstile-токены одноразовые и истекают, поэтому виджет нужно сбрасывать после каждого запроса.
