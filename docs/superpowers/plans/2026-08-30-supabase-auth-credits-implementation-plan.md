# План реализации регистрации и кредитов Supabase

> Основание: `docs/superpowers/specs/2026-08-30-supabase-auth-credits-design.md`

## Результат

На Vercel гость видит только страницу входа. После регистрации пользователь получает 5 кредитов, новый анализ расходует 1 кредит, баланс сохраняется в Supabase и не может быть изменён из браузера. Повтор сохранённого результата и один повтор LLM после ошибки не расходуют дополнительный кредит.

## Шаг 1. Подготовить зависимости и конфигурацию

Файлы:

- изменить `package.json` и `pnpm-lock.yaml`;
- изменить `.env.example`;
- изменить `README.md`.

Действия:

1. Установить `@supabase/supabase-js` и `@supabase/ssr` через pnpm.
2. Добавить в пример окружения:
   - `NEXT_PUBLIC_SUPABASE_URL`;
   - `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`.
3. Не добавлять service-role key: приложение работает от имени текущего пользователя, а права ограничивает RLS.
4. Обновить README: регистрация обязательна, начальный баланс — 5, кэш — 6 часов, старого браузерного лимита больше нет.

Проверка:

- `pnpm typecheck` после появления первых Supabase-модулей;
- `git diff --check`;
- убедиться, что `.env.local` и любые ключи остаются проигнорированными.

## Шаг 2. Создать воспроизводимую схему Supabase

Файлы:

- создать `supabase/config.toml` при инициализации CLI;
- создать `supabase/migrations/202608300001_auth_credits.sql`.

Миграция должна:

1. Создать `public.user_credits` с внешним ключом на `auth.users`, балансом `default 5`, ограничением `credits >= 0` и временными метками.
2. Создать `public.analysis_runs` с владельцем, параметрами поиска, флагом использованного повтора и датой.
3. Создать индекс по `analysis_runs(user_id, created_at desc)`.
4. Создать trigger-функцию и триггер, которые после вставки в `auth.users` создают баланс 5.
5. Включить RLS на обеих таблицах.
6. Разрешить роли `authenticated` только чтение собственных строк по `auth.uid() = user_id`.
7. Запретить клиентские `insert`, `update` и `delete`.
8. Создать атомарную RPC-функцию `public.consume_analysis_credit(query_text, location_text)`, которая:
   - берёт пользователя только из `auth.uid()`;
   - уменьшает баланс при `credits > 0`;
   - создаёт `analysis_runs`;
   - возвращает `run_id` и `remaining_credits`;
   - при нулевом балансе возвращает пустой результат, не меняя данные.
9. Создать атомарную RPC-функцию `public.claim_ai_retry(run_id)`, которая один раз меняет `ai_retry_used` только для владельца запуска.
10. Для всех `security definer` функций задать пустой/фиксированный `search_path` и использовать полные имена объектов.
11. Отозвать выполнение функций у `public` и `anon`, затем выдать его только `authenticated`.

Проверка до применения:

- проверить существующие таблицы и политики выбранного проекта;
- убедиться, что миграция не удаляет данные и повторно не выдаёт кредиты существующему пользователю;
- после применения запустить Supabase Security Advisor и Performance Advisor;
- выполнить SQL-проверки RLS, пяти списаний, шестого отказа и параллельного списания.

## Шаг 3. Создать Supabase-проект и применить миграцию

Внешние действия:

1. Создать проект `job-market-insights-alina-2026` в бесплатном аккаунте пользователя без перехода на платный тариф.
2. Выбрать ближайший доступный европейский регион.
3. Отключить обязательное подтверждение email для учебной версии.
4. Настроить Site URL для production Vercel и разрешённый локальный redirect URL.
5. Предпочтительно подключить официальный Supabase MCP через OAuth. Если в текущей сессии он по-прежнему недоступен, использовать официальный Dashboard/SQL Editor или CLI.
6. Применить миграцию и сохранить идентификатор проекта только в локальной/Vercel-конфигурации.
7. Добавить URL и publishable key в `.env.local`, не выводя их в логи и не коммитя.

Критерий:

- регистрация тестового пользователя создаёт строку `user_credits` с балансом 5;
- анонимный запрос к таблице не получает данные;
- пользователь читает только собственную строку.

## Шаг 4. Добавить серверную cookie-сессию Supabase

Файлы:

- создать `lib/supabase/server.ts`;
- создать `lib/supabase/proxy.ts`;
- создать корневой `proxy.ts`;
- создать `lib/auth/session.ts`.

Действия:

1. В `lib/supabase/server.ts` создать новый SSR-клиент на каждый запрос и подключить асинхронный Next.js `cookies()` adapter.
2. В `lib/supabase/proxy.ts` обновлять токены и передавать обновлённые cookies и запросу, и ответу.
3. В корневом `proxy.ts` исключить статические изображения и `_next`, но запускать обновление сессии для страниц и API.
4. В `lib/auth/session.ts` добавить серверные функции:
   - `getAuthenticatedUser()` через `supabase.auth.getClaims()`;
   - `requirePageAccount()` для redirect на `/login`;
   - `getApiAccount()` для ответа `401` без redirect;
   - чтение только `email` и собственного `credits`.
5. Не использовать `getSession()` как доказательство личности.
6. Не ограничивать безопасность только `proxy.ts`: страница и оба Route Handler выполняют собственную проверку.

Тесты:

- создать `lib/auth/session.test.ts` с mock Supabase-клиента;
- проверить отсутствие claims, корректный DTO и ошибку отсутствующей строки баланса.

## Шаг 5. Реализовать регистрацию, вход и выход

Файлы:

- создать `app/login/actions.ts`;
- создать `app/login/page.tsx`;
- создать `components/auth-form.tsx`;
- при необходимости дополнить `app/globals.css` только существующими дизайн-токенами.

Действия:

1. Валидировать email и пароль от 6 символов через Zod на сервере.
2. Реализовать Server Actions `signUp`, `signIn` и `signOut` через серверный Supabase-клиент.
3. Возвращать безопасные русские сообщения по коду ошибки, не показывая сырой ответ Supabase.
4. После успешной регистрации/входа перенаправлять на `/`; после выхода — на `/login`.
5. Авторизованного пользователя на `/login` перенаправлять на `/`.
6. Сделать один компактный экран с переключателем «Войти»/«Регистрация», состоянием загрузки и без 3D.

Тесты:

- корректный и некорректный email;
- пароль короче 6 символов;
- безопасное отображение ошибок «неверные данные» и «email уже зарегистрирован».

Действия:

2. Передать в `AccountProvider` минимальный DTO `{ email, credits }`.

Проверка:

## Шаг 7. Добавить серверный сервис кредитов

Файлы:

- создать `lib/credits/service.ts` и `lib/credits/service.test.ts`;
- изменить `lib/domain/stream-event.ts`.

Действия:

1. Обернуть RPC `consume_analysis_credit` в типизированную функцию с результатами `success`, `exhausted`, `unavailable`.
2. Обернуть `claim_ai_retry` в типизированную функцию с результатами `allowed`, `used_or_foreign`, `unavailable`.
3. Не принимать `user_id` от клиента: функции работают только с подтверждённой cookie-сессией и `auth.uid()`.
4. Добавить потоковое событие `credits` с `analysisRunId` и `remainingCredits`.

Тесты:

- успешное списание возвращает run ID и новый баланс;
- пустой результат RPC означает отсутствие кредитов;
- ошибка Supabase не маскируется под нулевой баланс;
- повтор различает разрешение, уже использованный/чужой запуск и сбой базы.

## Шаг 8. Встроить списание в основной анализ

Файлы:

- изменить `app/api/analyze/route.ts`;
- расширить `app/api/analyze/route.test.ts`.

Порядок Route Handler:

1. Подтвердить пользователя через `getClaims()`.
2. Валидировать размер тела, Zod и Turnstile.
3. Прочитать баланс и до Apify вернуть `credits_exhausted`, если он равен 0.
4. Выполнить поиск вакансий.
5. При ошибке или пустой выборке завершить без списания.
6. При непустой выборке вызвать атомарное списание.
7. Если параллельный запрос потратил последний кредит, завершить без выдачи отчёта с `credits_exhausted`.
8. Первым после списания отправить потоковое событие `credits`, затем вакансии, локальный отчёт и попытку LLM.
9. Логировать только request ID, user ID в сокращённом/хэшированном виде, run ID, новый баланс и этап; не логировать email и токены.

Новые тесты Route Handler:

- `401` без сессии и отсутствие вызовов Turnstile/Apify/LLM;
- нулевой баланс до поиска;
- ошибка и пустой результат Apify не вызывают списание;
- успешная выборка вызывает одно списание и отправляет событие `credits` до отчёта;
- ошибка базы после поиска не запускает LLM;
- AI fallback не возвращает кредит и сохраняет локальный отчёт.

## Шаг 9. Защитить один бесплатный повтор ИИ

Файлы:

- изменить `lib/domain/retry-analysis-schema.ts` и добавить тест;
- изменить `app/api/analyze/retry/route.ts`;
- создать `app/api/analyze/retry/route.test.ts`;
- изменить `components/market-console.tsx`.

Действия:

1. Требовать UUID `analysisRunId` вместе с уже существующими `facts` и Turnstile token.
2. Подтвердить сессию до обработки запроса.
3. Атомарно получить право на один повтор до обращения к OpenRouter.
4. Отклонять чужой, неизвестный или уже использованный запуск без вызова LLM.
5. В клиенте хранить run ID только для результата соответствующего анализа и скрывать кнопку после одной попытки.

Тесты:

- `401` без сессии;
- `400` без корректного run ID;
- чужой/использованный запуск не вызывает LLM;
- разрешённый запуск вызывает LLM один раз;
- повторный сбой LLM сохраняет резервный отчёт.

## Шаг 10. Упростить локальную историю

Файлы:

- изменить `lib/client/history.ts` и `lib/client/history.test.ts`;
- изменить `components/market-console.tsx`.

Действия:

1. Повысить версию хранилища до 5, чтобы старые записи без run ID не создавали неправильный бесплатный повтор.
2. Удалить `attempts`, `canStartAnalysis` и `registerAnalysisAttempt`.
3. Оставить шестичасовой кэш и максимум пять сохранённых результатов только как ограничение объёма localStorage.
4. Сохранять `analysisRunId` и обновлять баланс из события `credits`.
5. Обновить подпись под Turnstile: новый анализ расходует 1 из 5 кредитов, одинаковый сохранённый запрос бесплатен 6 часов.

Тесты:

- кэш живёт 6 часов;
- одинаковый ключ возвращает сохранённый результат;
- сохраняется run ID;
- старый формат v4 безопасно отбрасывается;
- число сохранённых результатов ограничено пятью, но запуск анализа браузером не блокируется.

## Шаг 11. Локальная проверка всего приложения

Команды:

1. `pnpm test`
2. `pnpm typecheck`
3. `pnpm build`
4. `git diff --check`

Сквозные сценарии на `http://localhost:3000`:

- гость перенаправлен на `/login`;
- регистрация сразу создаёт сессию и 5 кредитов;
- неверный пароль показывает русскую ошибку;

## Итоговый критерий готовности

Новый пользователь на production регистрируется без подтверждения почты, получает 5 кредитов, расходует их только на новые непустые анализы, не может изменить баланс или данные другого пользователя, видит сохранённый баланс после повторного входа, а шестой анализ при нуле не запускает внешние сервисы.
