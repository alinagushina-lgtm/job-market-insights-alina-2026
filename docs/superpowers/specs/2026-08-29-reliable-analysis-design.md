# Надёжный анализ вакансий — дизайн исправления

Дата: 2026-08-29

## Проблема

Публичный сервис загружает вакансии через Apify, а затем одним большим запросом передаёт до 20 вакансий в OpenRouter. Если OpenRouter возвращает временную ошибку, не отвечает вовремя или выдаёт неверный JSON, пользователь остаётся без отчёта и видит сообщение «Сервис анализа временно недоступен».

Проверка показала, что короткий запрос к настроенной модели проходит, но полный структурированный запрос на 20 вакансий может выполняться несколько минут. Отдельно Apify способен отвечать сетевой ошибкой `ECONNRESET`. Текущих журналов недостаточно для восстановления точного исторического HTTP-статуса.

## Цели

- Если найдена хотя бы одна вакансия, пользователь всегда получает содержательный отчёт.
- Сохранить AI-анализ OpenRouter как основной улучшенный результат.
- Показывать все найденные вакансии, но ограничить подробный LLM-анализ восемью наиболее подходящими.
- Ограничить время ожидания и число повторов внешних запросов.
- Сделать режим результата прозрачным: `AI-анализ` или `Резервный анализ`.
- Добавить диагностические журналы без ключей, полных текстов вакансий и персональных данных.
- Позволить повторить только AI-анализ без нового запуска Apify.

## Не входит в объём

- База данных, очередь фоновых задач и отдельный worker.
- Регистрация пользователей и серверная история отчётов.
- Изменение визуального стиля сайта или источника вакансий.
- Заявления о всём рынке на основании ограниченной выборки.

## Архитектура

### 1. Поиск вакансий

Apify загружает до 20 вакансий. Его ожидание и сетевые повторы ограничиваются общим временным бюджетом. После успешного поиска карточки всех вакансий сразу отправляются клиенту.

Если Apify не возвращает вакансии, сервис показывает точную ошибку поиска. Локальный отчёт в этом случае не создаётся, потому что у него нет фактов для анализа.

### 2. Гарантированный локальный отчёт

Сразу после получения вакансий сервер детерминированно создаёт резервный отчёт по всем найденным позициям и отправляет его клиенту до обращения к OpenRouter.

Отчёт использует только проверяемые факты:

- частоту навыков по всей выборке;
- редкие навыки;
- сопоставимые зарплаты;
- пересечение навыков пользователя с требованиями;
- наиболее частые отсутствующие навыки;
- уровень вакансии, формат работы и совпадение навыков для локального match score;
- практический план из трёх–пяти шагов, построенный по обнаруженным пробелам.

Если данных недостаточно, отчёт говорит об ограничении выборки и не придумывает требования.

### 3. Выбор вакансий для LLM

OpenRouter получает не более восьми вакансий. Они выбираются детерминированно по следующим признакам:

1. пересечение навыков с профилем пользователя;
2. совместимость уровня;
3. соответствие выбранному формату работы;
4. зарплатная группа;
5. исходный стабильный порядок как последний критерий.

Статистика `frequentSkills`, `rareSkills` и зарплатные факты по-прежнему вычисляется по всем 20 вакансиям. Описание каждой вакансии для LLM сокращается до безопасного лимита, достаточного для требований, но не создающего чрезмерный prompt.

### 4. OpenRouter

OpenRouter дополняет резервный отчёт персональными формулировками, типичными требованиями, объяснениями match score и планом действий.

Политика запроса:

- ограниченный общий временной бюджет;
- одна повторная попытка для сетевых ошибок, `429` и `5xx`;
- одна сокращённая попытка при неверном JSON;
- задержка между попытками;
- диагностический код сохраняется в журнале, но не раскрывает секреты или содержимое prompt.

Если AI-ответ успешно прошёл Zod-проверку, он заменяет резервный отчёт на клиенте. Если все попытки неудачны, резервный отчёт остаётся финальным результатом.

### 5. Повтор только AI-анализа

Кнопка «Повторить AI-анализ» отправляет на отдельный Route Handler только нормализованные данные максимум восьми выбранных вакансий, параметры поиска и профиль пользователя. Новый запуск Apify не выполняется.

Запрос имеет строгую Zod-схему, ограничение размера, Turnstile-проверку и тот же временной бюджет OpenRouter. При повторной неудаче текущий резервный отчёт не исчезает.

## Поток событий

1. Клиент отправляет форму и Turnstile-токен.
2. Сервер проверяет размер, схему и Turnstile.
3. Сервер пишет журнал начала поиска и вызывает Apify.
4. Клиент получает все вакансии.
5. Клиент получает локальный отчёт с режимом `fallback`.
6. Сервер выбирает до восьми вакансий и вызывает OpenRouter.
7. При успехе клиент получает обновлённый отчёт с режимом `ai`.
8. При неудаче клиент получает мягкое предупреждение, а резервный отчёт остаётся на экране.
9. Поток всегда завершается событием `complete` в пределах установленного бюджета.

## Интерфейс

- Над отчётом отображается метка `AI-анализ` или `Резервный анализ`.
- Резервный режим объясняется нейтрально: «Отчёт построен по данным найденных вакансий без внешней модели».
- Ошибка OpenRouter не отображается как отсутствие сервиса и не скрывает отчёт.
- После резервного результата доступна кнопка «Повторить AI-анализ».
- Карточки всех найденных вакансий остаются доступными независимо от результата LLM.

## Наблюдаемость

Каждый запрос получает `requestId`. Сервер записывает структурированные события:

- начало и завершение поиска;
- длительность Apify и количество вакансий;
- создание резервного отчёта;
- номер попытки OpenRouter, длительность, класс ошибки и HTTP-статус;
- режим финального отчёта;
- общую длительность запроса.

Не журналируются API-ключи, Turnstile-токены, полный профиль, полные описания вакансий или полный ответ модели.

## Тестирование

### Модульные тесты

- локальный отчёт для 1, 8 и 20 вакансий;
- детерминированный выбор восьми вакансий;
- локальные match score, сильные стороны, пробелы и roadmap;
- успех OpenRouter;
- сетевой сбой, `429`, `5xx`, таймаут и неверный JSON;
- сохранение резервного отчёта после неудачи LLM;
- строгая схема повторного AI-запроса.

### Интеграционные проверки

- 0 вакансий: понятное сообщение без отчёта;
- вакансии найдены, OpenRouter успешен: резервный отчёт заменяется AI-отчётом;
- вакансии найдены, OpenRouter недоступен: резервный отчёт остаётся;
- повтор AI-анализа не вызывает Apify;
- поток событий всегда завершается.

### Перед публикацией

- все тесты проходят;
- TypeScript проходит без ошибок;
- production-сборка Next.js успешна;
- проверочный Vercel-деплой имеет статус `READY`;
- публичный браузерный сценарий подтверждает вакансии и отчёт;
- свежие runtime-логи не содержат необработанных ошибок;
- production и GitHub обновляются только после успешной проверки.

## Критерии готовности

- При наличии вакансий пользователь всегда видит отчёт.
- Внешняя LLM не блокирует показ резервного результата.
- OpenRouter получает максимум восемь вакансий.
- Временные ошибки имеют ограниченные повторы и не создают многоминутного зависания.
- Режим отчёта виден пользователю.
- Повтор AI-анализа не запускает новый поиск вакансий.
- Ошибку можно диагностировать по свежим журналам без раскрытия чувствительных данных.
